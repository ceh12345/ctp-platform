# Sprint: Setup/Teardown Cascade on Unschedule

**Status:** 📋 Ready  
**Size:** ~2-3 hours CC work  
**Depends on:** Nothing — bug fix to existing functionality  
**Triggered by:** Bug found during UI review — bulk unschedule leaves orphaned setup/teardown tasks on the schedule

---

## Problem

The task list hides SETUP and TEARDOWN tasks by default (this is the correct default — planners don't want 3× the rows they care about). But this default creates three related bugs:

1. **Orphaned setup/teardown after unschedule.** When a planner selects PROCESS tasks in the list and clicks Unschedule, only the PROCESS tasks come off the schedule. The associated SETUP and TEARDOWN tasks remain on their resource, occupying capacity, with no process task between them. Setup and teardown have no independent purpose — they exist to serve a PROCESS task — so orphaned ones are a schedule inconsistency.

2. **Inaccurate count in selection chip.** The chip above the task list shows "N scheduled" where N is only the PROCESS task count. The actual count of tasks that would be affected by Unschedule is larger (N processes + N setups + N teardowns, potentially). The chip is lying about the scope of the action.

3. **Inaccurate toast after bulk action.** The success toast reports "Unscheduled N tasks" using the count from the selection, not the actual count of records the engine removed. After the fix, the real count may be larger.

### User-visible symptoms

- Planner unschedules 3 tasks
- Resource agenda still shows 6 committed slots (the 3 setups + 3 teardowns)
- Resource looks busy when it should be free
- Next solve may be affected by the orphaned commitments
- Planner thinks they freed up capacity but didn't

### Where the bug actually lives

This is not primarily a UI bug. The root cause is that `ScheduleEngine.unschedule()` treats each task as independent, when in reality SETUP and TEARDOWN are derived from their parent PROCESS task. The UI exposes the bug but the fix belongs in the engine — otherwise any other path that unschedules a task (API, AI recommendations, solver retry loops) has the same issue.

## Design

### Two types of state change tasks

The CTP model has two distinct kinds of setup/teardown tasks, and only one of them is affected by this bug:

| Type | How it's created | Scope | This bug? |
|------|------------------|-------|-----------|
| **Type 1 — Dynamic state changes** | Generated by `scheduleStateChangeTask` in basescheduler during schedule construction, based on resource state transitions (tooling/fixture/material changes). | Resource + state scope. A single state change can serve multiple compatible PROCESS tasks scheduled contiguously on the same resource. | **No.** Handled automatically by the engine — recomputed on every schedule operation. Not in the persistent data model as chain members. |
| **Type 2 — Route-defined setup/teardown** | Explicitly defined in the route alongside process tasks. First-class chain members with their own keys and linkId entries. The planner/ERP declared "this operation needs a setup, then a process, then a teardown." | Chain scope. Belongs to one specific chain. | **Yes.** This is the bug. |

**This sprint fixes Type 2 only.** Type 1 already behaves correctly.

### Core Principle

**Route-defined SETUP and TEARDOWN tasks belong to their chain.** If a chain has no scheduled PROCESS tasks remaining, the chain's SETUP and TEARDOWN tasks have no purpose and should be unscheduled too. If a chain still has at least one scheduled PROCESS task, leave the SETUP/TEARDOWN alone — they might still be needed.

The fix is a **chain-scoped sweep** after the main unschedule operation. Phase 1 removes exactly what was requested. Phase 2 sweeps the affected chains and removes orphaned route-defined state change tasks. This is garbage-collection-style rather than trying to trace per-task cascades.

### Why chain-scoped sweep over per-task cascade

- **Stateless.** Re-derives truth from current landscape state every time. No reference counts to maintain, no linkage metadata to drift.
- **Handles all operations uniformly.** Single, bulk, solver-internal, AI-driven — all code paths benefit from the same sweep.
- **Self-healing.** Orphans from any previous bug get cleaned up on the next operation. No data cleanup script needed.
- **Scales naturally.** Only sweeps chains that were actually touched by the operation. A 500-chain landscape with a 3-task unschedule sweeps 1 chain, not 500.
- **Simple invariant.** "After any unschedule operation, no chain has scheduled SETUP/TEARDOWN without at least one scheduled PROCESS." One rule.

### Three-layer fix

| Layer | Change | Why |
|-------|--------|-----|
| **Engine** | Add `sweepChainOrphanedStateChangeTasks()` after the main unschedule in `unscheduleBulk()` | Root cause fix. All callers benefit. |
| **API** | Bulk unschedule returns the full list of keys actually unscheduled with cascade counts | UI needs this to give accurate feedback. |
| **UI** | Confirmation dialog + toast + filter chip | Makes the cascade visible to the planner. |

## Deliverables

### 1. Engine fix — chain-scoped sweep in `unscheduleBulk()`

**Location:** `packages/engine/src/Solvers/BaseScheduler/basescheduler.ts` (or wherever the bulk unschedule lives)

The single `unschedule(task)` method stays simple — it removes exactly the task it was given. The cascade happens in `unscheduleBulk()`, which runs the main unschedule loop, tracks which chains were affected, then sweeps those chains for orphaned state change tasks.

```typescript
interface UnscheduleResult {
  requested: string[];    // Keys the caller asked to unschedule
  unscheduled: string[];  // Keys actually removed (includes cascaded setup/teardown)
  skipped: string[];      // Keys that couldn't be unscheduled (committed, running, already unscheduled)
}

interface BulkUnscheduleResult extends UnscheduleResult {
  processCount: number;          // PROCESS tasks removed
  cascadedSetupCount: number;    // SETUP tasks removed via sweep
  cascadedTeardownCount: number; // TEARDOWN tasks removed via sweep
  affectedChains: string[];      // Chains that were swept
}
```

**Bulk unschedule with chain sweep:**

```typescript
unscheduleBulk(landscape: ILandscape, taskKeys: string[]): BulkUnscheduleResult {
  const result: BulkUnscheduleResult = {
    requested: taskKeys,
    unscheduled: [],
    skipped: [],
    processCount: 0,
    cascadedSetupCount: 0,
    cascadedTeardownCount: 0,
    affectedChains: [],
  };

  const affectedChains = new Set<string>();

  // Phase 1: unschedule exactly what was requested
  for (const key of taskKeys) {
    const task = landscape.tasks.get(key);
    if (!task) {
      result.skipped.push(key);
      continue;
    }
    if (!this.canUnschedule(task)) {
      result.skipped.push(key);
      continue;
    }
    if (task.linkId?.name) {
      affectedChains.add(task.linkId.name);
    }
    this.removeFromLandscape(landscape, task);
    result.unscheduled.push(key);
    if (task.type === CTPTaskType.PROCESS) result.processCount++;
  }

  // Phase 2: sweep affected chains for orphaned route-defined setup/teardown
  const cascaded = this.sweepChainOrphanedStateChangeTasks(landscape, affectedChains);
  for (const key of cascaded) {
    result.unscheduled.push(key);
    const t = landscape.tasks.get(key);
    if (t?.type === CTPTaskType.SETUP) result.cascadedSetupCount++;
    if (t?.type === CTPTaskType.TEARDOWN) result.cascadedTeardownCount++;
  }

  result.affectedChains = Array.from(affectedChains);
  return result;
}
```

**The sweep helper:**

```typescript
private sweepChainOrphanedStateChangeTasks(
  landscape: ILandscape,
  affectedChains: Set<string>
): string[] {
  const removed: string[] = [];

  for (const chainName of affectedChains) {
    // Find all tasks in this chain
    const chainTasks = landscape.tasks
      .toArray()
      .filter(t => t.linkId?.name === chainName);

    // Does the chain still have any scheduled PROCESS task?
    const hasScheduledProcess = chainTasks.some(t =>
      t.type === CTPTaskType.PROCESS && t.isScheduled()
    );

    if (hasScheduledProcess) {
      continue;  // Chain still has work — leave setup/teardown alone
    }

    // Chain has no scheduled processes — remove any scheduled setup/teardown
    for (const task of chainTasks) {
      const isStateChange =
        task.type === CTPTaskType.SETUP || task.type === CTPTaskType.TEARDOWN;
      if (isStateChange && task.isScheduled() && this.canUnschedule(task)) {
        this.removeFromLandscape(landscape, task);
        removed.push(task.key);
      }
    }
  }

  return removed;
}
```

**Important — this fix targets Type 2 (route-defined) state change tasks only.** Type 1 dynamic state changes created by `scheduleStateChangeTask` are already handled correctly by the engine (recomputed on each schedule operation). CC should verify by inspecting `scheduleStateChangeTask` that Type 1 tasks don't appear as persistent chain members — if they do, the scope of this fix may need to expand.

**Single unschedule path:** The individual `unschedule(task)` method should also run the chain sweep for consistency, but since it only unschedules one task, the sweep only checks one chain. The implementation can share the same `sweepChainOrphanedStateChangeTasks` helper by passing a single-element set.

### 2. Edge cases to verify

The chain-scoped sweep handles these cases naturally:

| Scenario | Expected behavior |
|----------|-------------------|
| Chain with 1 PROCESS + 1 SETUP + 1 TEARDOWN, unschedule the PROCESS | Sweep removes SETUP and TEARDOWN |
| Chain with 3 PROCESS tasks + 1 SETUP + 1 TEARDOWN (shared), unschedule 1 PROCESS | Chain still has 2 scheduled PROCESS — sweep leaves SETUP and TEARDOWN alone |
| Chain with 3 PROCESS + 1 SETUP + 1 TEARDOWN, unschedule all 3 in one bulk call | Phase 1 removes all 3 PROCESS, Phase 2 sweeps the chain, finds no scheduled PROCESS, removes SETUP and TEARDOWN |
| Chain with multiple PROCESS each having their own SETUP/TEARDOWN (e.g. SETUP-A → PROC-A → TEARDOWN-A → SETUP-B → PROC-B → TEARDOWN-B), unschedule PROC-A only | Ambiguous — depends on whether SETUP-A and TEARDOWN-A are tied to PROC-A specifically or to the chain as a whole. See below. |
| Directly unschedule a SETUP task (via filter chip + explicit selection) | Phase 1 removes the SETUP. Phase 2 sweeps the chain — if PROCESS tasks remain scheduled, the sweep doesn't re-add anything. The planner gets what they asked for. |
| Mixed bulk of PROCESS and SETUP | Phase 1 removes both. Phase 2 sweeps for any remaining orphans. |
| Committed or running PROCESS in the chain | Phase 1 skips the committed task. Phase 2 sees a scheduled PROCESS still exists → leaves SETUP/TEARDOWN alone. |

**The ambiguous case (multiple PROCESS with individual setups in one chain):**

If a chain is structured as `SETUP-A → PROC-A → TEARDOWN-A → SETUP-B → PROC-B → TEARDOWN-B`, the current sweep logic treats the whole chain as a unit — it only removes setup/teardown when ALL processes in the chain are unscheduled. Unscheduling just PROC-A would leave SETUP-A and TEARDOWN-A on the schedule even though they serve only the (now unscheduled) PROC-A.

**Recommendation:** Start with the chain-as-a-unit approach (current spec). It's correct for the common case where a chain has one PROCESS with its setup/teardown. If Stafford's routes have multiple PROCESS tasks per chain with individual setups, this needs refinement — either per-task linkage on setup/teardown (a `forProcessKey` field), or position-based inference (SETUP-X serves the next PROCESS after it in sequence order). CC should check the Stafford data during implementation to confirm which chain structure is actually used before committing to a more complex approach.



### 3. API response

**Location:** `packages/api/src/modules/ctp/ctp.controller.ts` (bulk unschedule endpoint)

Current response probably just returns success + count. New response:

```typescript
interface BulkUnscheduleResponse {
  success: boolean;
  requestedCount: number;       // What the UI asked for
  unscheduledCount: number;     // Total tasks removed from schedule
  processCount: number;         // Of the unscheduled, how many were PROCESS
  setupCount: number;           // How many SETUP tasks were cascaded
  teardownCount: number;        // How many TEARDOWN tasks were cascaded
  skippedCount: number;
  unscheduledKeys: string[];    // Full list for UI to refresh
  skippedKeys: string[];
}
```

The UI uses these counts to build an accurate message.

### 4. UI — Confirmation dialog

**Location:** the bulk unschedule action handler in the task list / selection toolbar

Before calling the API, the UI needs to know how many setup/teardown tasks will cascade so the confirmation dialog is accurate. Two options:

**Option A (preferred): Compute client-side.** The task list already has the landscape loaded. For each selected task, find the associated SETUP/TEARDOWN tasks using the same linkage logic as the engine. This is read-only and fast.

**Option B: Preview endpoint.** Add `POST /ctp/unschedule/preview` that returns what *would* happen without actually unscheduling. More correct but adds a round-trip.

Start with Option A. If the linkage logic is too complex to duplicate client-side, fall back to Option B.

**Confirmation dialog copy:**

If no cascade:
> Unschedule 3 tasks? They will return to the Unscheduled panel.

If cascade:
> Unschedule 3 tasks and their 6 associated setup/teardown tasks? The setup and teardown will be removed from the schedule along with the process tasks.
>
> [Cancel] [Unschedule 9 tasks]

The button label shows the real total count.

### 5. UI — Toast after action

**Location:** bulk action success handler

Use the API response to build an accurate message:

```typescript
function buildUnscheduleToast(response: BulkUnscheduleResponse): string {
  if (response.setupCount === 0 && response.teardownCount === 0) {
    return `Unscheduled ${response.unscheduledCount} tasks`;
  }
  return `Unscheduled ${response.unscheduledCount} tasks (${response.processCount} process + ${response.setupCount} setup + ${response.teardownCount} teardown)`;
}
```

### 6. UI — Filter chip for setup/teardown visibility

**Location:** unified filter bar (`Status` row, or a new "Type" mini-row)

Add a filter chip labeled "Include setup/teardown" that, when toggled on, shows SETUP and TEARDOWN tasks in the task list. Default off.

When enabled:
- Task list shows all three types
- Selection chip count reflects whatever is actually selected (if the planner selects a setup task directly, it counts as 1)
- Bulk unschedule on a directly-selected setup task is allowed (edge case — probably rare but should work)

### 7. Selection chip tooltip

**Location:** the "N scheduled" chip above the task list

Add a tooltip that explains the count is PROCESS-only when the filter is off:

> 3 process tasks selected. Their associated setup/teardown will also be unscheduled if you click Unschedule.

This educates planners who are confused why the number they see isn't the number the toast reports.

## Out of Scope

- Changing the default filter state (setup/teardown should still be hidden by default)
- Changing how setup/teardown tasks are created or scheduled — only unschedule behavior changes
- Handling orphaned setup/teardown that already exist from previous buggy unschedule operations — those need a separate data cleanup script if the count is significant on existing tenants
- Extending the cascade to other task type relationships (this is specifically about SETUP/TEARDOWN → PROCESS)

*This is a small focused fix for a real user-visible bug. The engine-level fix is the important part — it prevents the same bug from recurring in any other unschedule code path. The UI changes are cosmetic improvements that make the cascade visible to the planner so they understand what's happening.*

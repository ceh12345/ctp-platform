# Sprint: Route-Defined Setup/Teardown Cascade in Solver `unschedule()` Path

**Status:** 📋 Ready
**Size:** ~30 min
**File:** `basescheduler.ts`
**Depends on:** `sprint-setup-teardown-unschedule-fix.md` — reuses the existing `sweepChainOrphanedStateChangeTasks()` helper and mirrors the pattern already established in `unscheduleBulkWithCascade()`.
**Triggered by:** Follow-up review — the parent sprint fixed the user-facing bulk path, but the solver-facing `unschedule(tasks: List<CTPTask>)` entry point still has the same bug.

---

## Problem

`BaseScheduler.unschedule(tasks: List<CTPTask>)` — the solver-facing bulk unschedule entry point at the bottom of `basescheduler.ts` — walks its task list and calls `unscheduleTask(task)` for each one. That inner call correctly cleans up **Type 1 dynamic state changes** (tooling/fixture/material transitions generated by the state change engine), but it does **nothing** about **Type 2 route-defined SETUP/TEARDOWN** tasks, which are first-class chain members.

Result: when the solver (or any caller of this method) unschedules a set of PROCESS tasks, the route-defined setup and teardown tasks for those chains remain scheduled on their resources with no process task between them — the same orphaned-setup/teardown bug the parent sprint describes, just reached via the solver path instead of the user-facing bulk path.

The user-facing path (`unscheduleBulkWithCascade`) already handles this correctly via a post-loop chain sweep. The solver path does not.

## Non-problem (important — do not change)

`unscheduleTask` calling `this.unScheduleStateChanges(task)` is **correct and must stay**. That method removes **Type 1 dynamic** state changes only — they are resource+state scoped and recomputed per operation, so per-task removal is the right behavior. Route-defined SETUP/TEARDOWN are a separate mechanism and are not touched by `unScheduleStateChanges`.

The two cleanup mechanisms are independent:

| Mechanism | Scope | Cleanup trigger | Where |
|---|---|---|---|
| Type 1 — dynamic state changes | resource + state | per-task | inside `unscheduleTask` via `unScheduleStateChanges` |
| Type 2 — route-defined SETUP/TEARDOWN | chain | post-loop sweep | **new** — in `unschedule(tasks)` after the forEach |

## Fix

Mirror the pattern from `unscheduleBulkWithCascade`: collect affected chain names during the loop, then call `sweepChainOrphanedStateChangeTasks` once after the loop completes.

### Change 1 — `unschedule(tasks: List<CTPTask>)` (bottom of file, ~line 1469)

**Before:**
```typescript
public unschedule(tasks: List<CTPTask>) {
  this.initUnScheduling(tasks);
  if (!this.assert()) return;

  this.startScheduling();
  tasks.forEach((task) => {
    this.startTask(task);
    this.unscheduleTask(task);
    this.endTask(task);
  });
  this.endScheduling();
}
```

**After:**
```typescript
public unschedule(tasks: List<CTPTask>) {
  this.initUnScheduling(tasks);
  if (!this.assert()) return;

  this.startScheduling();

  // Collect chains touched by this bulk unschedule so we can sweep
  // orphaned route-defined SETUP/TEARDOWN tasks (Type 2) ONCE after
  // the loop. Per-task sweeping would be wrong: a chain with shared
  // setup across multiple process tasks needs to be evaluated only
  // after all of that chain's removals in this batch are complete.
  // Type 1 dynamic state changes are still handled per-task inside
  // unscheduleTask via unScheduleStateChanges — that behavior is
  // unchanged.
  const affectedChains = new Set<string>();

  tasks.forEach((task) => {
    if (task.linkId?.name) affectedChains.add(task.linkId.name);
    this.startTask(task);
    this.unscheduleTask(task);
    this.endTask(task);
  });

  if (affectedChains.size > 0) {
    this.sweepChainOrphanedStateChangeTasks(affectedChains);
  }

  this.endScheduling();
}
```

### Change 2 — `unscheduleTask` (protected, ~line 406)

**No change.** Leave `this.unScheduleStateChanges(task)` in place. It handles Type 1 dynamic state changes, which is orthogonal to this fix.

## Invariant

After this fix, the following holds for **every** code path that ends in `BaseScheduler.unschedule(tasks)`:

> No chain has a scheduled route-defined SETUP or TEARDOWN task without at least one scheduled PROCESS task in that chain.

Combined with the existing guarantee in `unscheduleBulkWithCascade` and `unscheduleTaskWithStateChanges`, this means **all three public unschedule entry points** uphold the same invariant.

## Why this is the right scope

- **Solver paths benefit.** `unschedule(tasks)` is what the solver's retry/rework loop calls. Without this fix, solver-internal unschedules leave orphans even if the UI path is correct.
- **No behavior change for Type 1.** `unScheduleStateChanges` is untouched, so dynamic state change cleanup is unaffected.
- **Consistent with existing pattern.** `unscheduleBulkWithCascade` already does exactly this post-loop sweep. We're just adding the same two lines to the sibling method.
- **Chain-scoped, not task-scoped.** Handles the "3 processes share 1 setup, unschedule 2 of 3" case correctly — the sweep sees process #3 still scheduled and leaves the setup alone. A per-task sweep would incorrectly remove the setup the moment the first process is removed.

Reuse the scenarios from the parent sprint doc (`sprint-setup-teardown-unschedule-fix.md`), but exercise them through the `unschedule(tasks)` entry point rather than `unscheduleBulkWithCascade`:

| # | Scenario | Expected |
|---|---|---|
| 1 | Unschedule list of 1 process, chain has own setup/teardown | Sweep finds chain empty → setup + teardown removed |
| 2 | Unschedule list of 1 process, chain has no route setup/teardown | Sweep is a no-op |
| 3 | Unschedule list of 3 processes from 3 separate chains | All 3 chains swept; each chain's setup/teardown removed |
| 4 | Shared setup, 3 processes in chain, unschedule only 1 | Chain still has 2 scheduled processes; sweep leaves setup/teardown alone |
| 5 | Shared setup, 3 processes in chain, unschedule all 3 in one call | Loop removes all 3 processes, post-loop sweep sees empty chain, removes shared setup + teardown |
| 6 | Shared setup, 3 processes, unschedule 2 of 3 | Sweep sees 1 process still scheduled; setup/teardown untouched |
| 7 | List includes a task with no `linkId` | Task unscheduled normally; not added to `affectedChains`; no sweep triggered for it |
| 8 | Dynamic state changes present alongside route setup/teardown | Type 1 removed per-task by existing code; Type 2 removed by new post-loop sweep. Both mechanisms run; no double-cleanup, no missed cleanup. |
| 9 | Solver retry loop unschedules a partial batch | Orphans from this batch are cleaned up before `endScheduling()` runs, so subsequent solve sees a consistent landscape |
